# 产品能力评估与拓展规划

评估日期：2026-11-01。基于当前工作区源码、版本 0.1.0 及已有验收记录；这是规划建议，不表示新增功能已实现或接口已验证。

后续进展：本评估中的 15 个命令为搜索功能新增前的基线。现已优先增加 `docs search` 与 `docs read --name`，接口契约已核对、真实业务实测待完成，见 [SEARCH_API.md](SEARCH_API.md)。其余阶段建议不变。

## 1. 定位与建议

建议将 kunlun-cli 定位为：**面向 AI Agent 的昆仑智联办公执行工具，先把云文档的查找、理解、修改、核对做可靠，再扩展协作与结构化数据。**

当前最有价值的主线是“用自然语言维护操作规程、方案、纪要和周报”。先实现这条链路的稳定闭环，再依据部门试点反馈扩域。自然语言理解、草稿撰写和业务判断交给 Agent；CLI 提供确定性的业务动作、权限边界和可验证结果。

保留 TypeScript、现有分层和 Skill + CLI 路径。当前无需重写语言、引入插件框架或自建 Agent 平台。后续 MCP 与聊天入口复用业务服务和鉴权，不分别维护一套实现。

## 2. 现有能力：以代码为准

当前注册 **15 个命令路径**，其中 **5 个文档命令**；`--help`、`--version` 是额外开关，不计入路径数量。

- **应用配置：**`config init/show`。支持隐藏输入 Secret、环境变量覆盖、自定义私有化端点及配置目录；切换应用或主机时清理旧 session。Secret 和 token 目前存本地文件，文件权限设置不等于加密或系统密钥链。
- **本人授权：**`auth login/scopes/status/logout`。浏览器授权、本机回调、state 校验、token 自动刷新；固定四项业务 scope，仅允许显式选择子集。`auth scopes` 是版本目录，不是后台实时权限查询。默认 user，业务调用可显式选择 bot；bot 不应成为本人权限不足时的自动替代。
- **文档模板：**`docs template`。生成内置 UTF-8 操作文档模板，拒绝覆盖已有本地文件。
- **创建和追加：**`docs create/append`。支持正文文件、stdin 或短文本；创建可传 folder token；写入分批，每批最多 50 块。正文转换仅为普通段落及一至三级标题，空行和行首尾空白被去除，列表、代码块等不会被转换成对应的原生结构。
- **文档读取：**`docs read`。接受文档 ID 或链接，分页取块并转换为支持范围内的 Markdown 文本。当前没有读取完整性、结构丢失或省略内容的诊断字段。
- **定位修改：**`docs edit`。在受支持块中唯一匹配文本，支持联网预览及 `--revision` 乐观并发检查；只处理单个 text run 的段落或前三层标题，保留该 run 的已有样式；不支持跨 run、跨块替换和空字符串替换。
- **预览：**create/append 的 `--dry-run` 仅本地转换计数，不验证云端目标、目录权限或实际可写性；edit 的预览会鉴权并读取云端。两种预览的保证程度不同。
- **运行支撑：**`doctor` 探测平台、授权端点、应用凭证和登录态；它会联网，且可能获取并缓存 bot token，尚不是纯本地诊断工具。`skills install` 安装 shared/doc 两个 Skill；`api` 支持原始 HTTP 调用并限制请求源站；`version` 返回版本。
- **Agent 契约和交付：**业务结果采用 `{ok,data,error}` 风格 JSON，帮助为文本；已有分类错误、非零失败退出码、Windows 安装/PATH/覆盖更新脚本、哈希校验、隔离包测试和无运行时 npm 依赖的交付方式。

命令来源：[routes.ts](../src/cli/routes.ts)、[commands](../src/cli/commands)；业务边界来源：[service.ts](../src/domain/docs/service.ts)、[blocks.ts](../src/domain/docs/blocks.ts)、[edit.ts](../src/domain/docs/edit.ts)。

## 3. 实现与验收的差别

[验收记录](ACCEPTANCE.md)记载：用户授权、创建、追加、基础文本读取及简单文本修改有真实环境验证；固定四项 scope 一起授权有维护者反馈，Windows 安装更新有隔离和本机验收记录。

尚需补齐的证据包括：创建后连续写完正文的无中断流程、非维护者独立电脑接入、复杂内容、大文档分页、超过 50 块的真实写入、并发追加、bot 写入和指定目录。历史实测不代表当前工作区重新通过相同验收。

## 4. 与 lark-cli 对标的取舍

核对日期为 2026-11-01。官方 [larksuite/cli](https://github.com/larksuite/cli)展示了语义快捷命令、API 命令与原始 API 三层入口，配合 Agent Skills 和结构化结果，覆盖文档、云空间及其他办公域。

建议借鉴它的命令可发现性、业务语义封装和 Agent 工作流评估方式。昆仑的接口、身份、权限和块结构应独立核实；公有云接口存在，不代表私有化版本可用。当前已有语义命令和原始 API，中间的自动生成 API 命令层待接口规模与稳定性足够后再考虑。

衡量进度应使用“用户任务完成率、读回一致性、首次接入成功率和失败可恢复性”。命令数量作为能力目录信息即可。

## 5. 当前优先补齐的五个问题

### P0-1：让 Agent 知道读取了多少、遗漏了什么

`readDocument` 最多取 20 页，达到上限或 `has_more=true` 但无 token 时可能直接返回成功；转换器只提取部分文本，未知块与非 text_run 元素被省略。Agent 若据此改写文档，可能把无法读取的内容误判成不存在。

分别表达分页完整性和转换完整性；输出遗漏块 ID、类型、位置和原因。先报告限制，再逐步扩展格式。存在部分结果时也必须明确状态，不能以空文本替代未知内容。完整分页不等于完整理解。

### P0-2：把写入结果不明变成可核对、可恢复的状态

当前创建后写正文失败会尽量保留 document_id，这是正确基础。但分批追加缺少已完成批次信息、操作凭据与恢复策略；网络超时也不能证明服务端未写入。当前 CLI 不自动读回，验证要求主要在 Skill 中。

先补操作结果结构和读回核对：目标、操作、已确认完成的部分、结果是否确定、下一步建议。结果不明时先查证；无法确认则停止自动重放。平台不支持幂等键时，不承诺 exactly-once；本地 request ID 只能用于追踪。

### P0-3：将人工使用约定变成可执行的 Agent 契约

Route 当前只有 path、summary、run；除 auth 等局部命令外，没有统一的每命令参数白名单和 schema 校验，部分拼错参数可能被忽略。原始 `api` 默认可执行，Skill 仍允许其探索，而现有路线希望将它限制为开发者入口。

增加轻量命令描述：参数、输入输出、身份、所需能力、读写性质和预览语义。以一份定义生成帮助、参数校验及机器可读目录，避免三份手工维护。原始 API 在实际执行路径默认关闭，由维护者显式启用；Agent 不自行启用或改用 bot 绕过失败。

### P0-4：减少安装和登录求助

补充纯本地 `doctor` 模式，检查实际入口、Node/CLI 版本、配置目录、PATH、版本冲突和 Skill 兼容性；联网探测单独执行。登录已有固定 180 秒等待及清理逻辑，后续应增强超时配置、端口占用、取消/拒绝/换票失败的分类，以及失败保留旧登录态的验证。

### P0-5：将私有化兼容性留成证据

维护能力登记：接口及官方来源、平台版本/未知、身份、scope、已验证行为、验证日期及限制。区分“未验证、受支持、不支持、当前用户无权”，不依据一次 400/403 推断平台能力。先用少量脱敏夹具覆盖关键业务，再按实测扩展登记；不做启动时扫描全部接口。

## 6. 可以往哪里拓展

以下都是候选能力，命令名仅为设计草案，不可当作现有命令调用。

### 第一主线：从“给链接才能操作”到“找得到并维护得好”

**搜索和目录组织，优先级 P1。**先做名称/元数据检索、文件夹列表和资源类型识别，再评估全文检索；同名结果展示候选，记录 ID、类型、位置和可用链接。若全文搜索不可用，可交付有明确范围的目录浏览。随后逐项增加重命名、移动和归档；当前 drive 只读 scope 不能被假定支持写操作。

**复杂内容和章节编辑，优先级 P1。**按列表/代码块、链接与行内样式、表格、图片附件的顺序扩展。建立带层级及原始类型的文档模型，Markdown 作为一种表达。章节修改先定位到明确块集合，再预览、校验版本、写入并核对；不通过重建整篇文档实现局部修改。

**原生编号和正文评论，先做可行性验证。**它们已是现有使用反馈，适合安排小型验证任务；如果接口可用且投入可控，可在 P1 提前交付。验证编号增删章节后的原生重排、评论锚点在客户端的实际跳转；接口不支持时明确限制，手写数字和全文评论不可冒充原生功能。

**知识库和引用，优先级 P2。**核实 wiki 节点与 docx 等资源的映射，增加空间导航、多文档摘要、出处链接和块级定位。查询范围服从当前用户资源权限，初期不做全量知识库镜像和长期全文索引。

### 第二主线：让文档进入协作流程

**审阅协作，优先级 P2。**在正文评论验证通过后，扩展回复、解决状态和修改建议汇总，形成“收集意见—生成修改计划—按授权应用—读回核对”的流程。

**台账与周期汇报，优先级 P2。**Sheets 或多维表格只选一个先做，以本地需求和私有化可用性决定。第一版覆盖读取字段/区域、查询记录、追加记录和精确更新；先约定类型、日期时区、分页和批次失败语义，再做周报/问题台账模板。

**消息、日历和任务，优先级 P3。**在文档闭环稳定后接入“把已核对文档发到指定群”“把纪要待办写入任务”等明确动作。收件人、群、时间和发送内容需明确，按用户授权执行。定时任务和事件订阅等到有持久运行环境、去重和任务状态后再建设。

### 接入方式：按试点需要演进

本机 Skill + CLI 继续作为主路径。薄 MCP 适用于不能方便调用 Shell 的客户端；它复用 domain 和鉴权，CLI 的 stdout JSON 只属于传输适配层，不让 MCP 解析人类帮助文本。

“小惠”聊天入口和托管授权是独立部署形态。如果“同事不接触共享 Secret”成为部门试点前提，应将托管授权提前；否则在本机链路验证后再投入。服务端需要按用户隔离 token、聊天身份绑定、任务结果存储和撤销机制，不能共享维护者登录目录。

## 7. 优雅规范的实现约定

### 保留现有分层，按实际需要增加模块

- `cli`：解析、校验、帮助、结果输出；不拼业务 HTTP 流程。
- `domain/docs|drive|…`：可独立测试的业务动作和文档模型；返回类型化结果，不直接打印。
- `client`：源站约束、HTTP、超时、上游错误映射及请求追踪；只对明确安全的读取做有界重试，写入不盲目重试。
- `auth/config`：身份、scope、凭证生命周期；增加并发刷新锁和原子落盘时要有相应场景证据。
- Skill：任务选择、草稿、核对和失败处理；能力限制从同一命令描述派生，避免与 CLI 漂移。

新增分页工具应同时解决 read/edit 的游标上限、重复 token 和异常页面，避免只修读不修编辑。文档模型保留未知块和结构关系；暂不引入庞大的通用 AST 框架。

### 稳定的命令与输出

命令使用一致的 `kunlun <资源> <动作>`；沿用现有 docs 名称及已发布参数，不为形式统一随意破坏兼容性。新域初始只暴露验证过的语义命令。长正文优先 UTF-8 文件/stdin；分页、字段筛选和原始块输出按需启用，控制 Agent 上下文量。

保留 `ok/data/error` 信封，通过增量字段表达完整性、warnings、版本和部分完成情况；只有破坏性变更才升级契约。帮助和版本查询离线可用；日志进 stderr；Secret、token 和完整正文不进入默认诊断日志。固定 error.code 和恢复建议应便于 Agent 判断是否重新定位、重新授权或停止；网络写入错误不简单标成可重试。

### 写入保障与权限

预览明确说明验证范围；章节/文本编辑执行时绑定预览版本。读回验证关注目标块或区域，避免每次把整篇大文档灌入上下文。写入可能部分完成时保存可核对的目标和进度，不自动执行未经授权的反向修改作为“回滚”。

延续随 release 管理 scope 的策略。新增能力须完成私有化接口与身份验证后再加入权限清单；不允许 Agent 按上游报错临时扩权。系统密钥链作为本机凭证改进项，面向部门分发则明确共享应用 Secret 的配置责任。

## 8. 分阶段交付与验收

按顺序和退出条件排期，版本号为建议。每个阶段拆成可独立评审的小改动；具体日期和工期在接口验证及试点人数明确后估算。

### 0.2：可信文档执行底座（P0）

交付顺序：读取完整性 → 纯本地诊断 → 登录失败分类 → 命令参数契约及开发者 API 边界 → 写入结果、读回和恢复。最后两项可以拆为小版本，不要求一次“大重构”。

验收：异常分页和未知块明确标记；参数拼错在鉴权/写入前拒绝；首次接入能定位环境问题；写入超时先核对且不会自动重放；至少一位非维护者在独立电脑用 Agent 完成本人登录、创建、追加、修改和读回。更新测试、Skill、安装验收和实际云端证据。

### 0.3：文档维护闭环（P1）

交付搜索/目录浏览、列表与代码块、章节定位及版本检查；编号和锚定评论先验证，满足条件再并入。表格与图片拆开交付，不以“支持 Markdown”笼统承诺全部格式。

验收：用户仅提供名称时，Agent 能在授权范围内找到候选并消歧；章节修改保留非目标内容；列表层级和代码内容往返正确；不支持资源明确返回限制；新增接口各有本人身份的实测记录。

### 0.4：一个跨域办公场景（P2）

由试点选择“知识库资料汇总”或“台账生成周报”之一，只新增必要的资源域和 Skill。交付可重复的工作流配方、必要的来源引用、分步结果及失败恢复。

验收：相同任务在不同账号和真实样本上可完成；失败可指出具体步骤和已完成结果；资料来源可追溯，不把缺权或未读到的数据补成事实。

### 0.5 及以后：接入与协作扩展（P3）

根据使用数据决定 MCP、消息、日历、任务和聊天入口的投入。部门扩面前明确凭证方案、版本升级和成员退出流程；托管授权若是接入硬要求则前移，不受建议版本号约束。

## 9. 用场景验证产品价值

建立一个小型、版本化的场景集：从草稿创建操作规程；对已有规程做唯一修改；读取含表格/图片的文档并说明范围；同名文档定位；长文档中断恢复；两人并发编辑；新同事首次安装；权限不足时正确停止。每项记录 CLI/Skill 版本、账号类型、输入、预期结果、实际结果和证据，不存凭证与业务敏感正文。

建议将以下作为试点目标，尚无实测基线：

- 发布门槛：场景集中的“报告读取范围、版本冲突停止、结果不明不重放”全部通过。
- 真实任务完成率：首轮收集至少 20 次已授权任务，目标不低于 90%；未完成和中途退出计入分母，按原因记录，先建立基线再修订目标。
- 首次接入：至少 3 位非维护者独立安装授权并完成首篇文档，记录耗时和人工求助点。
- 质量观察：重复写入、误改目标和把部分读取声称为全文的事件逐次调查，不能由“平均成功率高”抵消。

## 10. 下一轮可以直接开工的改动

1. **读取结果表达完整性。**修改 docs service、blocks、输出类型和 Skill；覆盖异常分页、重复 token、混合未知块/行内元素。保持已有 markdown/block_count 字段可用。此项作为第一笔实现。
2. **纯本地 doctor。**不获取 token、不探测网络，报告入口和运行环境；为中文路径、低 Node 版本、多个安装位置提供可执行提示。
3. **登录失败收尾。**在现有 cleanup 基础上补分类、等待配置和失败后重登测试，不把已存在的超时清理当作全新功能重做。
4. **命令契约和 API 开关。**先以 docs 为样本统一参数声明、帮助和 schema，再推广；实际阻止默认 raw API，并同步 Skill。
5. **写入可恢复结果。**先记录批次与读回，覆盖“文档已建、正文部分完成、超时结果不明”；平台幂等和日志持久化另立验证任务。
