# 开发路线

更新日期：2026-10-29。当前统一发行版本 0.1.0，使用 TypeScript / Node.js。本机试用可重打包覆盖，下次正式分发递增版本号。此前 0.1.1 / 0.1.2 为未正式发布的实验编号；使用说明按 [README](../README.md) 分角色阅读。

## 目标和当前基础

近期优先完成“AI 编写并维护操作文档”，随后支持“小惠”部门试点。当前已具备配置、浏览器用户授权、版本固定 scope、token 刷新逻辑、通用 API、文档创建 / 追加 / 读取 / 唯一文本修改、JSON 输出和 Agent Skill。维护者反馈实际 Agent 已能初步登录和追加；实测范围见[验收记录](ACCEPTANCE.md)。

## 当前迭代：固定授权权限与 Agent 调用边界

根据 TODO 和维护者 2026-10-28 的确认，以下四项一起请求已完成真实用户登录验证；该证据不代表所有对应业务接口已验收：

- `docx:document`
- `drive:drive.metadata:readonly`
- `drive:drive:readonly`
- `space:document:retrieve`

权限集合由 `src/auth/scopes.ts` 随 CLI release 维护，不从 Agent 的任务或上游错误中临时扩展。默认 `auth login` 请求全部四项；兼容 `--scope` 选择非空子集，未知项、通配符和空值均在打开浏览器前拒绝。`auth scopes` 是本地版本权限目录，不是后台应用权限实时查询。其他 App ID 也遵守同一版本范围。

| 步骤 | 状态 | 修改内容与验收标准 |
| --- | --- | --- |
| 1. 固定 scope 与授权前检查 | 已完成源码及隔离安装验收，待正式发布 | 默认四项；只允许显式子集；拒绝拼错和重复参数；查询权限无需配置或联网；错误提示不引导扩大 scope；非法输入立即失败且不改凭证或登录态 |
| 2. 登录失败收尾 | 待实现 | 可配置等待时限；区分拒绝、超时、换票失败和授权不足；结束后释放端口，失败保留原登录态；测试无回调及失败后重新登录 |
| 3. 通用 API 开发者模式 | 待实现 | 保留接口探索实现，默认关闭原始 API 执行入口；仅隐藏帮助不算完成；显式启用后继续校验主机和调用身份 |
| 4. Agent 流程验收 | 部分完成 | 已同步登录指引，维护者反馈 Agent 初步登录和追加可用；后续配合开发者模式移除通用 API 兜底，验证未实现任务会明确说明限制、授权失败不会循环重试 |

发布顺序：后台新增用户身份权限并生效 → 维护者实测授权及相关接口 → 更新版本权限集合、业务封装、测试和 Skill → 递增版本并分发 → 用户升级并重新授权。后台增加权限不自动扩展旧版本请求；升级本地 CLI 也不自动扩大已有 token 的授权。无需因后台多开了暂不使用的权限就立刻发布，只有要交付对应能力时才纳入新版集合。

步骤 1 已提交；现有 180 秒回调等待仍保留，应用配置错误或授权页面无回调的体验归步骤 2。步骤编号保留原计划，实际交付顺序按下方最新使用反馈调整。开发者模式是产品调用约束，不能替代平台权限控制。每步单独检查、验收和提交。

## 根据实际 Agent 使用反馈调整交付顺序

2026-10-28 新增需求来自维护者更新的 TODO：原生标题自动编号、正文锚定评论、命令安装与 PATH 诊断、复杂内容读取完整性。先确保 Agent 正确理解已有文档，再扩展修改能力。

2026-10-29 按维护者要求先交付安装能力：新增 Windows 安装器及 `npm run install:local`，自动将固定安装目录加入用户 PATH，支持重新打包覆盖。隔离验收已验证同版本更新、旧包文件清理和凭证保留；本机真实安装及仓库外 CMD 的持久 PATH 解析也已通过。实际 Agent 需重启后试用，完整 doctor 诊断仍为后续任务。

| 顺序 | 交付内容 | 完成标准 |
| --- | --- | --- |
| 1 | 读取完整性标记 | 分别报告分页是否完整、内容转换是否完整；省略内容带块 ID、类型和原因；Agent 不把省略内容说成不存在 |
| 2 | 本地安装与 PATH 诊断 | 区分未安装、npm prefix 不在 PATH、旧 Agent 进程未继承环境、ps1 策略及版本冲突；从新终端和真实 Agent 均能找到预期版本 |
| 3 | 登录失败收尾与通用 API 开发者模式 | 分成两笔实现；无回调有明确超时结果，失败后可再次登录；默认阻止原始 API 执行，Agent 不自动开启模式 |
| 4 | 原生标题自动编号可行性与封装 | 先验证私有化接口能读写原生编号；支持时实现预览、设置和读回，增删章节后原生编号自动重排 |
| 5 | 原生正文锚定评论可行性与封装 | 验证当前平台的评论写入权限及锚点格式；创建后能在客户端定位到指定正文并读回评论 |
| 6 | Markdown 列表、代码块及复杂内容支持 | 步骤顺序、列表层级和命令格式正确往返；表格和截图另行分批实现，未支持部分继续明确标记 |
| 7 | 写入恢复、章节编辑与目录组织 | 写入不明先核对；章节修改检测版本冲突；按名称定位及目录操作逐个核实接口与权限 |

### 第一笔：让读取结果表达完整性

修改 `src/domain/docs/service.ts`、`blocks.ts`、CLI 输出和对应 Skill。保留已有 `markdown` 与 `block_count` 字段，新增结构化诊断，字段名在实现时定稿：

- 分页完整性与转换完整性分别表达；全部块已取回也可能仍无法完整呈现为 Markdown。
- 20 页上限、重复 page token、`has_more` 为真但缺 token 等情况不能静默当作全文成功。返回明确错误与可用的部分结果，防止无限分页。
- 跳过的块或行内元素记录类型、位置及原因，支持结构容器与其子内容的区分；部分内容被识别也不能掩盖同一块中其他元素被省略。
- 提供必要的块 ID、父子关系及可用的文档版本信息，供后续标题定位和评论锚定复用；原始块输出作为按需选项，避免每次给 Agent 灌入大量 JSON。
- 混合普通段落、列表和表格的测试，以及分页上限和异常游标测试通过。Agent 面对未完整呈现的文档应说明范围，不据此删除、重建或断言内容不存在。

本步先诚实报告省略，不要求一次实现所有列表、表格或富文本的保真转换。

### 第二笔：把安装问题变成可诊断结果

安装与更新入口已实现：`npm run install:local` 或交付目录的 `install.cmd`。安装器自动添加当前用户 PATH，首次安装后重启终端和 Agent；不修改系统 PATH。后续仍需补充以下诊断能力。

现有隔离包测试通过，只能证明安装入口可执行，不能证明真实 Agent 继承了正确 PATH。给 `doctor` 增加纯本地诊断入口（待实现），报告实际执行入口、CLI / Node 版本、npm 全局 prefix、命令解析位置和配置目录；无需登录或访问网络。未进入 PATH 时应能通过已知安装入口或源码构建入口启动诊断。

输出针对当前问题的修复步骤，不默认修改系统 PATH。验收包含中文目录、源码目录外执行、正常安装与隔离试用、多个版本并存，以及重启终端 / Agent 后的环境继承。维护者使用的已构建入口仍可用于开发，不作为同事安装完成的证明。

### 原生自动编号：先验证能力，再处理现有标题

先查当前昆仑私有化版本的官方接口和块结构，在明确的测试文档验证原生编号配置的读取、写入及客户端效果；公有云同名功能不直接视为可用。接口未支持时记录限制，不把手写数字前缀当作原生自动编号交付。

能力确认后，再封装标题层级读取、编号策略预览、原生编号设置及读回。清理人工编号必须在预览中逐项列出目标块和前后文本，保留可能属于标题内容的年份、型号等数字；执行前检查版本变化，失败时报告已完成部分。验收必须包含增删章节后的自动重排，避免同时出现人工编号与原生编号。

### 原生评论：区分全文评论与正文锚定

先验证评论创建 / 读取接口、用户身份、所需 scope 和正文锚点格式。当前四项权限是否足以创建评论仍待验证，不依据权限名称推断；确需新增时走固定权限 release 流程。

第一版只覆盖定位正文、预览锚点、创建及读回。重复文本需明确块和位置；正文变化导致锚点失效时停止并重新定位；创建结果不明时先查询核对，避免重复评论。客户端能跳转到正确正文才算锚定验收通过；全文评论需单独说明，不默默替代用户请求。回复、解决评论等管理能力后续按需求添加。

以上新增接口目前均为待验证或待实现项。本轮只提交既有授权功能并更新规划，不将需求清单视为接口支持证明。正式分发前，仍需一位非维护者在独立环境用 Agent 完成本人登录、追加及读回核对。

## “小惠”成员接入

### 近期：受控的本机 CLI 试点

成员使用同一个应用，每位同事在自己的运行环境中保存本人的用户登录态。维护者负责应用可用范围、用户身份 API 权限、程序版本分发和批准的密钥配置流程。

所有人使用同一无凭证安装包，通过本机 config init 配置 App ID 与隐藏输入的 Secret，再以本人账号授权。后续可接入系统密钥链改进本地存储；若希望同事完全不接触共享 Secret，则需托管授权服务。

### 后续：托管授权与聊天入口

若需要成员不接触应用密钥，或直接在“小惠”会话里请求任务，应单独设计服务端能力：

- 服务端保管应用密钥，按用户隔离 token，处理授权回调与刷新。
- 将聊天用户与授权用户可靠对应，拒绝使用其他成员的用户 token。
- 按用户授权和文档资源权限执行，写入前明确目标与内容。
- 处理任务结果返回、审计、失败恢复、成员退出和授权撤销。

这是待设计的服务端方案，不能仅把当前 `.kunlun-cli` 目录放到共享服务器上就视为完成。先选择受控 CLI 试点还是优先托管授权，再确定聊天功能排期。
